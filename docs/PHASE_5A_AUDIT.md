# Phase 5A requirement and implementation audit

Request: `phase5a-request.md`. Audit baseline: existing 71-table backend and Phase 4 passenger/admin app. Existing domain models, CRUD allowlist, enquiry engines, quality queries and React table/forms were reused. No parallel master-data database or duplicate CRUD endpoint family was created.

1. **Existing data-management audit — implemented.** Operators, stations, aliases, categories, vehicles, routes/stops, services, calendars, fares, platforms and observations already existed. Missing pieces were publication, persisted import previews, scoped identities, usable editors, dated rules and versioned rollback. Changes extend their existing modules.
2. **Central management — implemented.** Existing AdminPage/AdminTable now support operator scope, schemas, nullable references/JSON, database search/sort/filter/pagination, export, staged edits/deactivation, and role permissions. Added overview, scope selector and access administration. Batch imports and timetable shifting provide safe bulk changes.
3. **Import Center — implemented.** Local CSV/XLSX parsing, explicit column mapping, insert-only or explicit-ID update, row errors, transactional dry run, preview, independent approval, publication, verification links, history and supported rollback. Limits are explicit, not an unbounded background import service.
4. **Templates — implemented.** Existing Pydantic/SQLAlchemy definitions generate downloadable CSV and JSON specifications for all requested domains; JSON includes required/optional columns, types, keys, FK references, rules, code mappings and scope. Examples are labelled fictional and require replacement of local reference IDs.
5. **Stations/aliases — implemented.** Existing station/city/alias/bay records remain distinct. UTF-8 data, codes, alias types, active flags and stop boarding/alighting permissions are editable. Conflicting aliases are rejected. No fuzzy merge; Tirupati and Tirumala remain distinct.
6. **Categories — implemented.** Branded category, nullable facilities and reservation characteristics remain separate from vehicle type, individual vehicle and amenities. APSRTC setup stages the 13 requested brand names as user-provided configuration, with unknown facilities and no invented services.
7. **Routes — implemented.** Route editor creates or edits ordered stops, distances, elapsed arrival/departure offsets, permissions and direction; supports removal, reorder, copying routes, selected-stop variant creation and variant duplication. Backend validates the final bundle atomically.
8. **Services/timetables — implemented.** Existing service form gains depot/service type; calendars, vehicle assignments and stop times are editable. Timetable editor copies services, shifts schedules, previews calendars and saves unpublished bulk updates. Validated elapsed offsets cross midnight without same-day arithmetic.
9. **Fares — implemented.** Existing segments/stages, tables, rules, concessions and trip overrides are managed with Decimal. Added effective windows and surcharges, overlap checks, rollback-only draft calculation preview and audit/fare history. The system does not infer passenger eligibility for concessions.
10. **Platforms — implemented.** Existing timed, sourced, verified platform records are scoped and staged. Every published change is audited; enquiries retain freshness/unknown distinctions.
11. **Exceptions — implemented.** Calendar exceptions carry reason/type/details and support added/cancelled/suspended/festival service, departure change, diversion, partial stop cancellation and temporary boarding restriction. Published exceptions affect enquiry queries immediately.
12. **Validation — implemented.** Schema/foreign-key/ownership/provenance checks, natural-key duplicates, aliases, ordered route/time/distance rules, calendars, fare dates/amounts/overlap, exception details and platform location checks. Publication blocks critical row failures. Dashboard levels retain legacy ERROR/WARNING/INFO plus enterprise HIGH/MEDIUM/LOW mappings; staged integrity failures are CRITICAL.
13. **Publication — implemented.** DRAFT → VALIDATED → APPROVED → PUBLISHED → ARCHIVED. Creator cannot approve own draft. Scope is enforced by the backend; production defaults to staging even through legacy CRUD/CSV routes. Only an explicitly configured root demo/test mode permits direct writes.
14. **Versioning/rollback — implemented with declared eligibility.** Existing import batches and audit logs hold checksum, workflow, revision, actors, before/after/changed fields and record versions. Rollback appends audit history and rejects newer edits or dependent records. Legacy batches without snapshots are explicitly ineligible. Missing rows never imply deletion.
15. **Quality — implemented.** Actual scoped SQL counts and paginated affected records cover missing fares/times/platforms, categories, stale observations, duplicates, invalid sequences, calendar conflicts, dated rules, failed staged imports and workflow queue. Existing QualityIssue records support recorded resolution. Correcting generated findings removes them on the next live audit; it does not mark broken records as repaired.
16. **NLP/enquiry integration — implemented.** Aliases/categories are read from the database, not trained into static entity lists. Approved schedules, effective fares, cancellations and platform changes are visible to fresh requests. Session fare-rule caching invalidates on flush; no new global reference cache.
17. **APIs — implemented.** Existing versioned master endpoints remain; action endpoints handle staging, mapping, validation, approval, publication, rollback, templates, scoped export, previews and audit. Authentication, capabilities, ownership, pagination, bounded files/rows and safe HTTP errors are enforced server-side.
18. **Offline/databases — implemented and exercised.** Parsing, validation and application queries use local libraries/database only. Tests block external backend socket connections and browser requests. Both SQLite and a locally installed PostgreSQL test database execute real transaction tests. OS firewall isolation is not claimed.
19. **Tests — implemented.** `backend/tests/test_data_management.py` covers all 28 requested test categories against actual SQLite/PostgreSQL databases. `frontend/tests/data-management.spec.ts` exercises real production-bundle workflows. Exact final counts and commands are in PHASE_5A_REPORT.md.
20. **Acceptance — verified by the report's recorded checks.** Real import → review → publication → passenger lookup → rollback is exercised, together with regression tests and incremental migration preservation. No official APSRTC operational dataset was supplied or fabricated.
21. **Deliverables — implemented.** Import Center, management forms, route/timetable editors, fare preview, exceptions, publication/rollback, quality, audit, templates, tests and setup/report documentation exist in the repository.

Schema preservation evidence: `phase5a-live-migration.json` checks every pre-existing column value in the actual 71-table SQLite database against its backup (1,112 rows). `phase5a-migration-verification.json` records separate SQLite/PostgreSQL upgrade tests. Original migrations 0001–0010 were preserved; 0011–0014 are incremental.
