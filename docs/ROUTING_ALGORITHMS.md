# Local time-dependent routing

RouteSearch.timed_paths extends the existing route finder. Each label contains physical station, earliest boardable timestamp, dated service legs, visited stations and accumulated wait. Outgoing segments come exclusively from Repository.journeys, with actual stop IDs and ordered route/variant membership. Stops reachable on active services are queried through indexed station/route foreign keys; the planner never iterates every station pair across the whole network. No city-name merging or inferred taxi links occurs.

The search enumerates feasible labels using a bounded frontier, retaining separate histories to preserve fare, duration and transfer alternatives. It is a timetable-dependent path enumeration algorithm, not ordinary shortest-path search on a static city graph. Reboarding the same dated service and revisiting a station are rejected; at most three bus legs are permitted. Transfers require arrival plus minimum connection time, per-transfer maximum waiting and cumulative maximum waiting. Departure windows apply to the initial leg, while arrival deadlines and final filters apply to the complete journey.

This deliberately favors correctness of short itineraries over premature label pruning: earlier arrival does not necessarily dominate a cheaper journey with a different onward wait bound or visited history. Optional Pareto filtering runs on complete itineraries with known fares, considering arrival, fare, transfers and wait. Unknown fares are never assigned zero. Equal ranking scores sort by arrival, departure and stable journey ID. A resource-truncated search cannot establish global optimality; the response explicitly reports this.

TimetableBatch prefetches bounded stops, calendar exceptions, calendars, dated trips, tariffs, fare overrides and fresh verified stop observations. Vehicle metadata and active disruption records are fetched in batches when reachable services are discovered. All caches are request-scoped. Database edits become visible on the next request; there is no persistent route cache or network fetch.

Bounds: public horizon1-48hours,0-2transfers, expansion budget1-20000,100 reachable destination stations per expansion,1000 default/10000 maximum services per segment,20000 rows per timetable batch query, and2000 complete candidates for quadratic Pareto filtering. Existing FK indexes cover station/route, service/date and trip lookups. Additional composite trip-stop-freshness and service-calendar date indexes should be assessed against realistic PostgreSQL query plans before production deployment; no unmeasured index benefit is claimed.

Trade-offs: recurring services are expanded from calendars and stop offsets, with null trip_id when no dated operational record exists. Verified fresh stop-time changes can alter feasibility; stale information falls back to schedule. Station-local timezone conversion is used, but multi-timezone route-origin conventions and DST cases have not been comprehensively verified. Existing departure-delay propagation produces estimated, never live/verified arrival claims. Dense branching networks may exhaust resource limits. No RAPTOR/CSA-scale throughput or globally optimal national routing claim is made.
