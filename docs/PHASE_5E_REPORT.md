# Phase 5E implementation and verification

**PHASE 5E INCOMPLETE.** The implemented infrastructure is tested locally, but OS-isolated offline certification, installed service/reboot recovery and physical multi-terminal LAN/TLS acceptance remain unverified. The Windows account is not an administrator, and WSL/Linux is not installed. No Phase 6 or speech work was started.

## Infrastructure audit and changes

The audit covered startup, FastAPI/static serving, database creation/pooling, English model cache and registry gates, persistent context/session ownership, expiry tooling, Alembic, dispatcher WebSockets, request logs, configuration, bearer authorization and available backup/deployment scripts. The concrete gaps and their outcomes are:

1. **Deployment modes:** explicit standalone SQLite / central PostgreSQL mode validation now refuses cross-mode DB fallback. Actual managed startup was exercised for both modes on this host; central clients were simulated over loopback, not certified on a physical LAN.
2. **Startup:** old startup applied migrations and could seed during launch. Windows now delegates to one production Python entry point; Linux wrapper provided. Startup checks local assets, config, credentials, actual schema head, DB connectivity and optional model load, takes an OS instance lock and never installs/downloads/migrates. Controlled migration procedure is separate.
3. **Process recovery:** Linux systemd service/timer and explicit Windows Task Scheduler installer supplied. Real API crashes, manual restarts, preserved selected-journey sessions, duplicate startup refusal and graceful control-file shutdown were exercised. Installed auto-restart/reboot behavior remains untested.
4. **Offline assets/models:** existing production assets remain local. Approved model requirements remain unchanged; optional missing model yields degraded deterministic service. Cache is bounded to four loaded versions. Corrupt/missing artifact rejection is tested; no weights or active registry were changed. No production approved model exists, so model-inference performance cannot be claimed.
5. **Sessions:** existing unique owner-bound IDs, per-tab storage, idempotent receipts, atomic context updates, kiosk inactivity reset and result references are preserved. Managed runtime adds bounded periodic expiry cleanup and visible maintenance status.
6. **Database:** added pool pre-ping, bounded pool/overflow, recycle/checkout/connect/statement timeouts for PostgreSQL while preserving URL search-path options. SQLite adds busy timeout, WAL and foreign-key enforcement. Real PostgreSQL shutdown produced readiness 503; restarting it restored connectivity without restarting the API. SQLite retains its single-writer limits.
7. **Events:** existing WebSocket now observes public audit changes beyond dispatcher events, including master/publication changes. Reconnect starts with authoritative invalidation/refetch; client versions reject duplicates/outdated messages. Passenger chat adds connection status and refresh guidance; existing staff/board behavior remains. There is no external broker or per-client delivery-ack claim.
8. **Snapshots:** portable versioned/checksummed SQLite exports from either DB exclude private sessions, credentials, feedback, raw imports and unverified operational records. Source/schema/validity and safe import provenance are included. Production exports reject DEMO contamination and require site identity.
9. **Reconciliation:** trusted manifest hash plus explicit current fingerprint and offline application lock are required. A transaction replaces central masters while preserving local private data; divergent operational evidence, orphaned references, changed schema/authority and older packages fail closed. Duplicate imports do not replay. Interrupted-import rollback and invalid/corrupt package rejection are tested.
10. **Backup/restore:** consistent SQLite backups, PostgreSQL custom dumps, registry/nonsecret config exports, manifests, verification, retention command and local schedule templates implemented. Real isolated SQLite restore and PostgreSQL dump/restore passed. Restore cannot overwrite an existing destination or nonempty PostgreSQL database. Private backup copies remain ignored by Git.
11. **Security:** existing backend capability hashing, owner isolation, admin/operator/station scopes, input/import limits, rate limits and same-origin policy remain. Strict launcher requires a strong-length private root capability and exact LAN trusted hosts; proxy forwarding headers are not trusted. TLS/firewall/secret ACL deployment instructions are provided, but not installed or certified on this host.
12. **Health/observability:** public liveness/readiness and authenticated dependency diagnostics added and connected to System Status. Actual disk/RSS, sampled latency/error rates, active sessions, background cleanup, DB and publication evidence are exposed. Logs are bounded/rotated and omit passenger bodies, secrets and raw URLs. Global log-family age retention still needs OS configuration.

## Performance observations

Hardware: Windows 11 build 26200; Intel Family 6 Model 151; 6 physical / 12 logical cores; approximately 34.19 GB RAM. One Uvicorn worker, local DB, seeded labelled DEMO data, deterministic fallback. Each load level uses one six-request multi-turn workload per simulated kiosk: next departure, selection, fare, stops, connecting enquiry and follow-up. The benchmark verifies that initial selection has real matching services. Connecting enquiries may truthfully return no connection where the dataset has no suitable onward service.

Final 1/5/10/25/50-kiosk measurements, P50/P95/P99, throughput, errors, server CPU/RSS and per-response DB/intent timing samples are in `phase5e-benchmark-sqlite.json` and `phase5e-benchmark-postgres.json`. These are short local functional load samples, not an SLA or endurance certification. Debug timing adds overhead; other validation jobs also ran on this host. “Intent inference” measures deterministic interpretation here; trained-model latency is unavailable.

At 50 kiosks, the final SQLite sample had P50 **1,604 ms**, P95 **4,039 ms**, P99 **13,830 ms**, **17.23 requests/s** and zero errors; sampled RSS peaked at **134.8 MB**, server CPU **87.5%**. PostgreSQL had P50 **2,654 ms**, P95 **4,772 ms**, P99 **4,893 ms**, **14.37 requests/s** and zero errors; sampled RSS peaked at **149.6 MB**, server CPU **98.1%**. Different data sizes and concurrent host work limit direct engine comparisons.

The initial SQLite 50-kiosk trial returned 8/300 errors and P95 about 12 seconds; a repeat completed without errors. This variability is a genuine standalone capacity concern. A PostgreSQL trial without current demo services was excluded as an empty-data baseline. Another PostgreSQL trial hit the normal per-IP rate limit because all kiosks shared loopback; it is retained separately. Final capacity runs raise the request limit only in the benchmark process; normal runtime retains its 300-write/minute/IP policy. Do not silently use the failed or empty trials as successful capacity evidence.

## Remaining acceptance gates and limitations

- Public-internet disconnection using OS firewall/network isolation has **not** been performed. Current Windows token is not administrative; Linux/WSL is absent. No complete offline certification is claimed.
- Systemd and scheduled-task definitions have not been installed, rebooted or crash-tested as OS services. Linux shell/service operation is provided but unverified on this host.
- Central PostgreSQL mode was tested locally, including outage/recovery and browser serving. Physical LAN loss/reconnect across separate terminals, local TLS trust and firewall exposure still require a deployment test bed. Current HTTP loopback tests are not a substitute for secured LAN deployment.
- No approved active English statistical model is available. Essential deterministic service remains available and health correctly says degraded; production model accuracy/latency/readiness cannot be invented.
- A single central machine remains a single point of failure. Backups and restart mechanisms provide recovery, not HA/failover. No broker, replication cluster or distributed model registry was introduced.
- Snapshot reconciliation is an explicit stopped-kiosk administrative action. It does not synchronize passenger conversations centrally or automatically merge dispatcher conflicts. Transfer authenticity depends on a separately trusted manifest checksum and protected local transfer.
- Backups include private DB records and credential hashes. Protect backups and separately preserve model files/private configuration; approved encryption and off-device copies are deployment responsibilities. Per-process log rotation needs an OS age/retention policy across old PID families.
- Sustained-load, power-loss and disk-full endurance testing remain unperformed. The disk warning and interrupted operations were safely simulated rather than filling or damaging the user's drive.
